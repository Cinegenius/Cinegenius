# Work Mail – review candidate, 22 November 2026

The approved “both” choice is implemented as two independent entry paths: a private forwarding address and delegated read-only Gmail/Microsoft connections. The source is reviewable; no receiving domain, DNS record, OAuth app, secret, production schema, deployment, provider request, or real message has been created or activated by this work.

## Implemented behavior

`/work/mail` is an authenticated private Work page. The native Tools tile uses the existing closed `.workMail` relay and current workspace/account check to the scene's existing main web view. It creates no second CineGenius controller, header, push owner, or Genie. All API reads and writes derive ownership from fresh Clerk authentication and require the same account in `X-Mail-Account`. Writes additionally require an exact trusted same-origin request. The optional native presentation signal only changes how the browser connection action is shown; it grants no access.

The forwarding address is an unpredictable 192-bit local part on a configured, dedicated receiving subdomain. Create/pause/resume/rotate are account scoped. Rotating invalidates the old alias; pausing stops Work from accepting its deliveries. Sender names and mail bodies never establish account identity. A delivery resolves exactly one active alias.

The receiving endpoint is `/api/webhooks/work-mail`, under the existing signed-provider webhook exception in Proxy. It validates Svix over the exact bounded payload and accepts only `email.received`. The verified event contains metadata; content comes from the fixed Resend Receiving API, followed only by a fresh HTTPS download URL on the exact `inbound-cdn.resend.com` host, with no redirect or credential forwarding. Unknown hosts fail closed. No sender URL, arbitrary attachment URL, remote HTML image, script, or active message HTML is rendered or fetched.

Original MIME bytes are stored unchanged and immutable in the private `work-mail-private` bucket. An account-scoped reservation, original SHA256 and stable external key make retries idempotent. Writes become visible only after storage acknowledgement; a lost acknowledgement succeeds only if an existing immutable object is byte-identical. Forwarded mail is marked received, not automatically imported until the member explicitly imports the selected message. After that explicit import, the private Dispo analysis starts automatically through the existing personal native Genie contract. The analysis source is the current received Dispo PDF selected from that message with extractable text; if no PDF is present, the message plain text is used for this first functional pass. No message is published, distributed, sent, or copied into a project.

The existing-mailbox path uses delegated OAuth authorization code + PKCE S256, a secure HttpOnly SameSite=Lax encrypted state cookie, fresh Clerk account/session binding and an atomically consumed ten-minute state hash. Refresh/access tokens are sealed server-side with AES-256-GCM and account/provider/connection associated data. Refresh claims prevent simultaneous rotation against the same connection. Provider import reservation/commit and disconnect share the same owner lock; a removed connection cannot make a pending source visible. Only `gmail.readonly`, or Microsoft delegated `Mail.Read` plus `offline_access`, are requested. The app cannot send, modify or delete provider mail. After a mailbox has been connected, the UI starts a bounded current-Dispo search over the newest provider page. It scores subject/from/attachment metadata for Dispo/call-sheet signals, imports only the best clear message, then starts the existing private Dispo analysis from that imported message.

A short provider list remains available as a fallback when the automatic metadata search does not find a clear Dispo candidate. The automatic analysis is scoped to one imported received Dispo message and its selected current Dispo PDF/text source; there is still no entire-mailbox sync, background polling or backfill. Disconnect removes local encrypted credentials. Gmail revocation is attempted and its project-wide grant consequence is explained. Microsoft has no equivalent least-privilege per-token revocation API here; the UI honestly instructs the member to remove remaining app consent in their Microsoft account. Stored originals and already cached attachments remain private and available after disconnect. An uncached attachment requires its original connection.

Native OAuth starts in the system browser **before** creating state, because the pinned Capacitor handler opens external provider navigation in Safari and WKWebView cookies would not follow it. The native view therefore offers a fixed `/work/mail` browser link; the member signs into the same CineGenius account there, connects, then returns to the app and refreshes. No cookie, credential or account ID is passed in the link.

Selected file preparation uses an account-bound streaming endpoint, a size bound and SHA256 verification. Verified bytes are returned in64KiB chunks to use the platform's streaming response path rather than a large buffered response; actual hosted12MiB behavior remains an activation check. The member then separately taps Save/share. Web Share is used where available; a native renderer without it offers the browser page. The automatic Dispo path reuses the same owner-bound attachment reader for PDF text extraction, limits it to the existing 12MiB attachment bound and the Dispo document limits, and treats extracted text only as untrusted source data. The native source has no `WKDownloadDelegate` or existing blob-file importer.

## Limits and database boundary

The exact reviewed SQL remains in `supabase/candidates/work_mail.sql`. Root subsequently generated `supabase/migrations/20261122161546_work_mail.sql` with pinned Supabase CLI2.81.3, copied the tested SQL body, and recorded its hash. It has not been applied to production. Production has no application migration registry; compare the real catalog and apply only this reviewed change, never blindly push the historical migration folder.

Five tables use RLS with all PUBLIC/anon/authenticated privileges revoked. Only server `service_role` receives table and procedure access. Procedures are `SECURITY INVOKER`; browser clients cannot supply a privileged actor through Data API RPC. The private bucket is created only by the reviewed migration, and the candidate rejects an existing public bucket of that name. A restrictive Storage objects policy also blocks all anon/authenticated access to this bucket even when unrelated legacy permissive policies exist; service access remains server-only. File readers never return public or signed storage URLs. The shared image optimizer explicitly excludes `/api/work/mail` sources, including encoded/normalized aliases.

Bounds are 12 MiB per unchanged original or selected attachment, 20 attachment entries, 200 messages and 100 MiB of reserved original/cached attachment bytes per account. The webhook is at most64KiB; parsed provider JSON and preview text are separately bounded. API/provider operations have deadlines; clients abort on account/navigation/background changes and recheck ownership/epoch after asynchronous work, including hashing. No stale private result may repopulate the view after revocation.

A failed original upload can leave a non-visible reserved item; retrying the same selected source resumes it safely. The current candidate does not add destructive archive deletion, a retention daemon, or automatic quota expansion. Operators must review these conservative limits and pending-reservation administration before broad activation. No existing user archive or public storage access is changed by the source candidate.

## API / future native import contract

All private requests require current Clerk cookies plus `X-Mail-Account: <current verified account>`. The header is a binding check, not authentication by itself. Mutations also require trusted same-origin context.

- `GET /api/work/mail` → `{accountId, capabilities, alias, connections, items, cursor}`. A missing schema yields disabled capabilities; it never falls back to public data.
- `GET /api/work/mail?connection=<UUID>&cursor=<opaque>` → one bounded provider list, only when the member opens the fallback list.
- `POST /api/work/mail` → explicit alias/connect/disconnect/import/current-Dispo-search operation. Client actor/owner claims cannot override the fresh Clerk account.
- `GET /api/work/mail?item=<UUID>` → selected owner-bound preview, unchanged-original metadata and attachment entries. Original metadata contains `name`, `type`, `size`, `sha256`, `downloadPath`. Attachment IDs are server-owned SHA256 references, with optional `sha256`/`cached` when already cached.
- `GET /api/work/mail/items/<UUID>/file[?attachment=<64hex>]` → bounded inert bytes, `Content-Disposition: attachment`, `Content-Type: application/octet-stream`, `Content-Length`, `X-Content-SHA256`, `nosniff`, sandbox CSP and private/no-store headers. No arbitrary URL input. The reader rechecks ownership for every request.

A future native project-import bridge must take only these closed IDs and explicit message/attachment/project selection, revalidate current account/read state/size/hash, and use the existing native document importer. The current automatic Dispo path treats extracted PDF text or imported message text only as untrusted source data for the existing personal Dispo contract; it does not treat mail content as instructions.
