# Native Smart entry before a text search

This is an app-only entry at `/search?smart=1` when there is no `q`, `plan` or refinement context. `UnifiedSearchResults` chooses it only when the existing native appearance hook is active. The ordinary website, existing text interpretation, explicit plans and all current Smart-admin gates retain their original route.

## Real data and access

`GET /api/native/v1/discovery?focus=profile|neutral` uses Clerk's current authenticated identity and `unifiedSearchAccess(...).canReadResults` before reading a profile or executing search. A native HTML marker or custom header never grants access. Guests receive401 and ordinary members403 `in_development`; they see the existing clearly illustrative development preview (when signed in) plus genuine Crew `/creators`, marketplace `/props`, Locations `/locations` and companies `/companies` links. This is not an aggregate/map entitlement for members.

Admin requests require `X-CineGenius-Native-Discovery: cinegenius.native-discovery.v1` and `X-Native-Account` equal to the current authenticated account; mismatch409. Unexpected query parameters are rejected. The existing per-account unified-search40/minute quota is reused. All JSON, including errors, is private/no-store for browser and CDN. Response: `{contract,accountId,serverNow,focus,plan,groups}`. The client checks this account/plan envelope, drops stale/aborted responses, and uses the existing `SmartSearchExplorer` for combined areas, cards, list, map/list, cursors, result identity and privacy-aware detail links. It does not cache/persist result rows.

The initial plan is six **existing generic version1 wishes**: Crew, marketplace, Locations, companies, Jobs and Projects. This is the existing six-wish plan ceiling, not a claim of ten real backend domains. Other actual search domains remain available through a deliberate text query. `executeUnifiedSearch(...,'map')` returns its bounded, permission-projected public result pool, including unmapped records; no new query/parser/permission engine or model call is introduced. Subsequent paging remains the shared search API. Profile visibility, linked identities, map opt-outs and approximate location rules remain in the shared projector before public points or this focus ordering.

## Explicit profile focus

Only the current account's saved, unambiguously resolved occupations and its verified canonical city supply focus. No occupation or availability is inferred from a broad profile type, a photo, a company, free-text behavior or activity. Multiple saved departments remain possible. An unresolved/missing focus is neutral; a profile read failure is a visible error rather than an invented empty/successful profile. Switching to Neutral skips the profile query entirely. Editing focus reuses the actual `/profile` form; this entry does not silently update a profile.

Profile focus sorts **the already loaded authorized pool**, keeping its IDs, public fields, unknown availability, grouping and server cursors unchanged. Own department matches are preferred in Crew, then distance between existing public map points and the current account's canonical city centre. Unknown/hidden points are not guessed or geocoded. It is not global catalogue ranking and not an exact-person-distance guarantee. It never removes other departments, areas or distant entries. Manual search and explicit shared filters still take precedence. A private wishlist could become an additional consciously chosen source later; this change does not inspect it or add browsing-history tracking, user embeddings, analytics or model training.

## Lifecycle and UI

The entry verifies matching active Clerk `useAuth`/`useSession` identities and keys its account child by account/session. Account/session transitions synchronously remove result controls. Requests are abortable, bounded to25seconds client/20seconds server, and revalidate on foreground/focus/pageshow/app-resume with a small duplicate-event debounce. A current401/403 returns to the development fallback;409 or other failures show retry. No background polling or interpretation is started merely by entering Smart. Controls/focus mode may restore on the real account-owned history entry through existing `useViewState`; fetched rows, private city/occupation data and media never enter history or persistent storage. Keyboard submission navigates to the unchanged explicit Smart text-search flow.

No large visible area heading is added. The accessible heading remains present. Search follows the approved glass treatment and inherits the shared theme tokens; controls have44px minimum targets. Seventeen catalogues contain the new small `NativeSmartDiscovery` namespace. Results use the existing Explorer and its five primary area controls rather than a duplicate result renderer.

## Verification boundary

Targeted synthetic route tests cover gate ordering, account/header/query/quota validation, profile/neutral behavior, errors/cancellation and public-pool ordering without data loss. Actual React static rendering uses all seventeen real catalogues and covers session mismatch and directory fallbacks. Lint/typechecks are recorded in `research/native-smart-discovery-source-stable.safe.json`. There were no real profile/database/provider requests, build, deployment or device changes in this task. Combined real browser loading/cursors/map/keyboard, actual server latency and a signed-in iPhone acceptance remain separate. This source change does not grant broader Smart access or make the test prototype's fictional tenth domain real.
